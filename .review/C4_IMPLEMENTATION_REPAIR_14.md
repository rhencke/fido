## 1. The defect

`elaborate_indexed` constructs one exact causal chain — `Compilable.Input` → `Compilable.Phase` →
`Compilable.WorkForest` + `Compilable.WorkIndex` → `Compilable.TypeNameFacts` → `Compilable.Outcomes` + `Compilable.Trace` →
`Compilable.AnnotatedWork` → `Compilable.ExpressionFacts` → `Compilable.Diagnostics` — and then **discards it**.

On success `Compilable.Facts` retains selected projections. `Compilable.Program` retains `Compilable.source`,
`Compilable.program_index`, `Compilable.facts`, and `cp_prov : elaborate Compilable.source = …`. That equality is in `Prop`, is erased, and its
right-hand side contains only the already-stripped result: it is not the causal object and cannot project it.
The present "object identity" theorems expose the loss by *rebuilding* — calling `build_compilation_input` and
`build_expression_phase` again and proving the stored projections equal independently recomputed ones. On
failure, `ElaborationFailed` / `Compilable.Failure` retain only a flattened diagnostic list.

This is the rejected provenance pattern at the final boundary: build the exact object → discard it → retain
selected outputs → rerun the builders → use equality as provenance. Future `Safe.Program` proofs and user
extensions cannot consume the accepted C4 causal object; they must reconstruct it. **No green proof or test
command can repair a constructor topology that does not retain the object.**

Repair 13 is correct and stays: one immutable source authority, one retained `Compilable.Input`, one
proof-carrying `Compilable.WorkForest`, the exact standard-map-backed `Compilable.WorkIndex` built once, no production
`List.find` key lookup, exact `WorkMember`/`SuffixMember`/`Compilable.Conversion`/`ConversionStep` identity, one
`Compilable.Accumulator` and intrinsic `Compilable.Trace`, exact final-to-tail causal preservation, one dependent
`Compilable.Phase`, exact source `Syntax.TypeExpr`/operand identity, exact diagnostic identity, one `Typing.convert_constant`,
unchanged generated bytes, no C5.
