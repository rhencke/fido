## 1. Purpose

Remove every byte with no present, load-bearing purpose.

Git owns archaeology. Current source states what is true now. It does not explain what used to exist, which
repair introduced a form, which candidate failed, or how a name changed.

M1 reduces stale or repeated comments, source archaeology, comments that restate clear code, duplicate
architecture prose, superseded plans, reviews, reports and compatibility narratives, dead files, and dead
declarations, theorems, examples, aliases, wrappers, fixtures and imports.

M1 does not reduce correctness, theorem strength, exact retained provenance, constructor or mint topology,
current local comprehension, current FCB authority, unsupported-boundary precision, enforcement, generated
artifacts, or reviewed behaviour.

There is no byte quota. Formal compliance through a weak cosmetic edit is not completion. The review judges
whether every retained byte has a current purpose and whether the reduction is real.

## 2. Strict scope

**M1 may** delete or rewrite comments and prose; delete whole dead declarations and their now-unused imports;
delete whole dead files; delete superseded review and design artifacts whose current content is already owned
elsewhere or is history only; remove duplicate current-state text from non-owning documents; shorten current
documentation without weakening it; add the one source-diet checker and its permanent exception ledger; add
the temporary baseline, metrics, file-disposition and deletion ledgers the review needs; and wire the checker
into working-tree and staged-snapshot verification once the tree complies.

**M1 may not** change a surviving Rocq declaration's name, type, body, theorem statement, constructor topology
or proof body; introduce a new abstraction, wrapper, alias, notation, module, compatibility path or
replacement theorem; split, merge, rename or move modules; restructure proof dependencies; optimise or
refactor algorithms; alter a checker, build stage, cache, Make target, Dune graph, Docker graph or hook beyond
adding the narrow M1 gate and the active-matrix subject; change Go meaning, accepted or rejected program sets,
diagnostics, trust boundaries, extraction, transport, generated bytes or runtime output; rewrite a current FCB
rule into a weaker or less exact summary; or perform M2, M3 or M4 work.

A surviving declaration is byte-stable apart from comments and the whitespace their removal leaves. **If
deleting a dead declaration would force a surviving declaration or proof to change, stop and report that
dependency.** Do not inline, duplicate, generalise or rewrite it under M1.

### Classification

| Finding | Disposition |
|---|---|
| stale prose, comments, dead files, dead declarations | M1 |
| build time, dependency fan-out, cache cost | record for M2 |
| tool factoring, host and container placement, duplicate gates | record for M3 |

Discovery does not determine scope.

## 4. The comment law

Every comment in every tracked or untracked-nonignored `.v` file, including the proof gate and the end-to-end
witnesses.

A **default** comment is one logical block on one physical line, at most 120 characters from opening to
closing delimiter, at most one sentence, one current local fact, with its owner obvious from the adjacent
code, and no archaeology. Leading indentation outside the delimiter does not count; both delimiters do.

A comment that merely restates the next name, definition, theorem statement or obvious proof step is deleted.

**The gate is necessary, never sufficient.** It rejects only unambiguous syntactic classes — over-length,
multi-sentence, archaeology, documentation markers, banners, decorative glyphs, identifier-only comments,
`H<n> = ...` proof-case labels and `this member is ...` bullet labels. Passing it does not make a comment
earn its place. A human reads every surviving comment and deletes any that only paraphrases the declaration
below it, narrates a proof, expands a field name, or repeats architecture the types or the FCB already carry.
That human review is part of the accepted gate, and no checker claims to replace it.

**Adjacency.** Comment tokens separated only by whitespace are ONE logical block, so a stack of one-liners and
two comments on one line are each one block and neither evades the rule. Only real code separates blocks.

**Sentences.** A `.`, `?` or `!` ends a sentence when followed by closing punctuation and then whitespace or
the end of the body, so a qualified name such as `Compilable.Program` is safe. Do not game the counter with
semicolons or fragments; human review is authoritative over meaning.

**Archaeology and placeholders are rejected**: a numbered repair, a candidate, a commit hash, "formerly",
"previously", "used to", "renamed", "migration", "legacy", "deprecated", "superseded", "old name",
"historical", "introduced in", "removed in", "retired in", "before this change", "after this change", and
TODO, FIXME, XXX, temporary, placeholder, compatibility and future-use notes. Ordinary ordering words such as
"before the operand" are current algorithmic language, not archaeology.

**Delete outright**: section banners and comment art; theorem inventories; consumer lists; lists of
unsupported syntax the FCB already owns; repeated one-authority claims; proof narration restating each tactic;
comments whose only content is a declaration's English expansion; comments explaining a deleted design;
checkpoint, repair, campaign, migration or candidate state; comments preserved for generated documentation;
empty comments. Use names, types, module boundaries and theorem statements instead.

## 5. Rare exceptions

A longer comment survives only under one exact ledger row. It attaches directly to one named declaration or
file module with only whitespace between, uses one allowed category, occupies at most four physical lines,
keeps every line at or below 120 characters, carries no archaeology, has an exact SHA-256 over its UTF-8
token, and states why the name, type, theorem statement or nearby code cannot carry the fact.

Allowed categories: `invariant-not-expressed-by-type`, `trust-or-effect-boundary`, `non-obvious-proof-plan`,
`rocq-limitation-forcing-shape`.

The gate is bidirectional and fails on: an exception without a row; a row without its exact comment; a hash
mismatch; a missing or ambiguous owner; a row whose owner was deleted; duplicate rows; duplicate ownership; an
unapproved category; more than four lines; any line over 120 characters.

**The goal is zero exceptions.** A large ledger is evidence that M1 failed, even when the parser reports
green.

## 6. The checker

`tools/source-diet.py` is one narrow checker and measurement tool. Its PERMANENT modes are `--self-test`, <!-- FIDO-FCB-REF:TOOLS-SOURCE-DIET-PY -->
`--check`, `--wiring`, `--measure`, `--write-metrics`, `--root` and `--snapshot`; writer and checker share
one implementation. Its M1 EXIT modes are `--m1-self-test`, `--against-baseline`, `--disposition-exact`,
`--code-identical`, `--write-disposition`, `--write-metrics-table` and `--verify-m1-evidence`, and no
permanent path invokes one. Two further modes carry §8 and §11, which the required six state but cannot check:
`--against-baseline` compares the candidate to the sealed baseline and fails unless every required metric
decreased and every required count is zero, and `--code-identical <ref>` (or `baseline`, which reads the
sealed ref) proves EXACT TOP-LEVEL COMMAND EQUALITY: after removing exactly the complete declaration units
the deletion ledger names, the remaining command stream of every `.v` file equals the candidate's, in order.

A declaration unit is that declaration's own command, plus — only when a `Proof` command follows it — its
proof commands and its exact terminator. It is nothing else. An `Arguments`, `Hint`, `Opaque`, `Transparent`,
`Existing Instance`, `End`, `Import`, `Export`, `Open Scope`, `Close Scope`, `Set` or `Unset` beside a
declaration is its own unit, so deleting the declaration cannot silently delete it too. Whether a declaration
is proof-bearing is decided by the command that FOLLOWS it, never by whether its text contains `:=`, because
a theorem statement may carry `:=` and still open a proof. A shape the model cannot classify raises and names
the file and command; it never guesses.

Its comment scanner is a Rocq lexer, never a regular expression: comments nest, strings may contain comment
delimiters, and comments may contain strings. It preserves exact UTF-8 tokens for hashing, reports
unterminated comments and strings, fails closed on unreadable or invalid UTF-8, identifies logical adjacency,
and resolves an exception's owner structurally rather than by line number.

Working-tree mode enumerates tracked plus untracked-nonignored files through Git and fails if enumeration
fails. Snapshot mode checks the supplied exported tree with no dependence on the caller's working tree.
Neither silently scans zero files.

Its root enforcement helpers are covered by `tools/gate-mutation-test.py`: deleting each helper's effect must <!-- FIDO-FCB-REF:TOOLS-GATE-MUTATION-TEST-PY -->
make that helper's own named controls fail. Those mutants split by lifetime too — the permanent run exercises
`--self-test`, and `--m1` exercises `--m1-self-test` — so no M1-only helper is kept alive by the permanent
gate.

Once the tree complies, `diet` joins the `Makefile`, `check` depends on it, and `.githooks/pre-commit` runs <!-- FIDO-FCB-REF:GITHOOKS-PRE-COMMIT --> <!-- FIDO-FCB-REF:MAKEFILE -->
the staged copy against the exported staged tree, self-tests first in both paths. Both run the permanent
modes only, and `--wiring` fails if either regains a checkpoint-only one. The build graph is not
otherwise restructured; M3 owns that.

## 7. File and document review

Review every tracked file, not only recently changed ones.

For technical sources — Rocq, Python, shell, OCaml, the container build, the Makefile, Dune files and hooks —
retain a comment only when it explains a current local fact that the code does not; remove history and
duplicated architecture; delete dead helpers and dead files; keep behaviour unchanged; do not refactor tool
architecture. The hard one-line 120-character gate is enforced for Rocq; other technical comments follow the
same terse current-fact style under review rather than through the Rocq lexer.

The FCB may stay long where it owns exact normative content: governance decisions and the rationale needed to
apply them, amendment register rows, fixed points, closure and latitude rows, exact contracts and theorem
surfaces, current unsupported boundaries, and current consultation and ownership rules. Remove duplicate
current-state prose, repair and candidate narrative, history already in Git, a law restated by a non-owner,
and references to superseded plans with no current normative content. **Do not weaken a rule to shorten it.**
Where two documents duplicate one authority, keep the more basic owner and make the other point at it tersely
or delete it.

A review, plan, audit or report survives only when a current authority or accepted contract still consumes its
exact content. History-only directives, closure audits, migration plans and status reports are deleted, and a
deleted historical document is not replaced by a new summary of its history.

`CLAUDE.md`, `ARCHITECTURE.md`, `PROGRESS.md`, `PAINFUL_LESSONS.md` and the other root documents each need one
current purpose; remove what the FCB or `.review/NEXT_STEPS.md` already owns. Do not delete unique current
operating law, binding architecture, explicit rejected-shape lessons or technical frontier information merely
because a file is large. `life.md` is current character-continuity, not technical authority; keep technical
history out of it and do not rewrite its character content under M1 without Rob's separate authorization.

## 8. Measurement and required direction

One implementation produces the same metric set for baseline and candidate: repository file count and total
bytes; a deterministic compressed archive size; `.v` file count, total, comment, non-comment and percentage
bytes; comment block, physical-line, default, exception, multiline, over-120 and archaeology counts; root,
proof-gate and end-to-end `.v` bytes; current-FCB, other-review, root-markdown, tool, build-file, plugin and
generated-artifact bytes; Rocq definition, theorem, example, instance and module counts; and deleted file and
declaration counts. Per-file bytes live in the file-disposition ledger.

The compressed measurement is a deterministic archive — path-sorted entries, fixed timestamp, fixed owner and
group, modes derived from the snapshot, no build residue, and gzip with no embedded timestamp — produced by
the same implementation for both sides.

M1 may not request review unless total tracked bytes, `.v` comment bytes, `.v` comment physical lines and
deterministic compressed bytes all decrease; multiline non-exception comments, over-120 non-exception comments
and archaeology comments are all zero; and every increase in a kept file is explained by an enforcement or
current-authority need. No percentage target is imposed. Rob judges whether the reduction is sufficient.

## 9. Declaration deletion law

Before deleting a declaration: search code, the FCB, contracts, ledgers, gates, extraction, the plugin, the
end-to-end witnesses, generated artifacts and public examples; identify every current consumer; prove the
surface absent, strictly superseded, duplicate, compatibility-only or fixture-duplicate; add its ledger row;
delete its gate entry if that entry was its only consumer; remove newly unused imports; and run the full proof
and end-to-end gates.

Do not call a declaration dead because a text search finds no consumer, when dependent types, notation,
typeclass resolution, extraction or plugin lookup may consume it. A deleted public theorem is a review finding
even when the build stays green, and its ledger row must explain why it is not an accepted public guarantee.
No surviving declaration changes. No replacement aliases.

## 10. Work order

Authority commit; baseline capture against that exact ref; foundation Rocq comments; the index and typing
layers; the admissibility layer; safety, rendering and emission; the proof gate and end-to-end witnesses;
non-Rocq technical comments; root and review prose and dead files; dead declarations and imports in small

documentation-only freeze requesting review.

Every scripted edit asserts its exact expected match count before writing. No unchecked global replacement, and
no bulk deletion commit that hides what survived. Run the full gate after every declaration or file deletion
group. Do not wire the comment gate into the hook until the source satisfies it, then prove both modes.
